# Task B — SDD-інструмент: OpenSpec

**Інструмент:** OpenSpec 1.12.0 (`@fission-ai/openspec`), схема `spec-driven`
**Вхід:** `docs/spec/pricing-discounts.md` (Task A) — 24 рішення, 28 критеріїв
**Вихід:** `openspec/changes/add-discount-engine/` — 8 вимог, 28 сценаріїв, 28 задач
**Дата прогону:** 2026-09-06 · **Оновлено:** 2026-09-08 — D-24 і критерії
AC-24…AC-28 додано за результатами рев'ю вже після першого прогону; лічильники
нижче наведено за поточним станом артефактів.

Обрано за вартістю входу: це Node-CLI, а Node у репо вже є, тоді як Spec Kit і
BMAD потребують ще й `uv`.

## 1. Що він згенерував (сам)

| Команда | Що дала |
|---|---|
| `openspec init` | `config.yaml` (робочий рядок один: `schema: spec-driven`), порожні `specs/` і `changes/archive/` |
| `openspec new change add-discount-engine` | теку зміни, `.openspec.yaml` і `README.md` — **і жодного з чотирьох артефактів** |
| `openspec instructions <artifact>` | вказівки, що має бути в артефакті (є й `--json`) |
| `openspec validate … --type change --strict` | перевірку формату |

Каркас — від інструмента, зміст — із Task A: кожен сценарій названий за ID
`AC-N`. Це і є цикл, по якому Task B просить прогнати специфікацію.

| Артефакт | Роль у схемі | Що всередині |
|---|---|---|
| `proposal.md` | навіщо / що зміниться / capabilities | одна нова capability `pricing-discounts` |
| `specs/pricing-discounts/spec.md` | delta: SHALL/MUST + WHEN/THEN | 8 вимог, 28 сценаріїв |
| `design.md` | як лягає в код | залишки `R[c]`, `options.now`, без float |
| `tasks.md` | чекліст готовності | 28 задач у 8 групах |

У PR їде лише `openspec/` — файли інтеграції з редактором під `.gitignore`.

## 2. Що він дав понад markdown

| Що | Доказ |
|---|---|
| **Порядок артефактів, який не обійти** | `openspec status` одразу після створення: `[-] tasks (blocked by: specs, design)` — почати з плану реалізації неможливо |
| **Exit-код для CI** | `openspec validate --strict` → `exit 1` на структурній помилці; markdown у пайплайн не ставиться взагалі |
| **Специфікація як дані** | `openspec show --json --deltas-only` → `deltaCount: 8`, кожен сценарій окремим об'єктом: можна рахувати покриття й дифати версії |
| **Облік плану** | `openspec list` → `0/28 tasks`; прогрес Task C видно командою, а не переглядом файлу |

**І зауваження до моєї ж Task A.** Критерій із `openspec instructions specs` —
«якщо реалізацію можна змінити, не змінивши зовнішньо видимої поведінки, це не
spec» — робить **§3.1 моєї специфікації (алгоритм із `R[c]` і формулою
округлення) design'ом, а не spec'ом**. Рознесла: поведінка → `spec.md`, модель
і компроміси → `design.md`. Сама б я цього не помітила.

## 3. Чого він не дав

**Головний результат: він гарантує форму, а не зміст** — чотири артефакти на
місці й структурно валідні, і нічого про те, чи закриті в них рішення.
Перевірила навмисними поламками й порівнянням із ручним рев'ю:

| Що перевіряла | Що сказав OpenSpec |
|---|---|
| вимога без **жодного** сценарію | `✗ ERROR`, `exit 1` — єдине, що він ловить |
| сценарій знижено з `####` до `###` | `ℹ INFO`, **valid**, `exit 0` — вимога тихо втратила один сценарій із двох |
| `## Purpose` скорочено до 10 символів | **valid**, `exit 0` — правило «50+ characters» з його ж шаблона на дельті не діє |
| специфікація з невизначеною поведінкою (D-22, знайдено вручну) | **valid**, `exit 0`, `4/4 artifacts complete` |
| арифметика критеріїв: `100 000 × 10 % = 12 000` | не перевіряє взагалі — числа підтвердили окремий скрипт і тести Task C |
| розвилки в тікеті (24 рішення) | не знайшов жодної |

Тобто від втрати покриття захищає не валідатор, а таблиця простежуваності
Task C. Окремо: бібліотеки специфікацій ще немає — `openspec list --specs` →
«No specs found», бо дельти стають головними специфікаціями лише після
`archive`/`sync`; `doctor` на однозмінному репо теж мовчить.

## 4. Що лишилось руками

- **Усі рішення** — пошук розвилок і обґрунтування кожної.
- **Усі числа** — і їх перевірка окремим скриптом.
- **Межі вимог** — 28 критеріїв у 8 вимог: інструмент вимагає ≥1 сценарій на
  вимогу, але не підказує, де межа між вимогами.
- **Спільні ідентифікатори** — `AC-N` у назвах сценаріїв, щоб Task A,
  `openspec/` і тести Task C говорили однією мовою.
- **Мова артефактів** — англійська, бо формат тримається на `SHALL`/`WHEN`/`THEN`.

## 5. Висновок

**Для фічі такого розміру доброго markdown вистачило б** — жодного рішення
інструмент за мене не прийняв. Але три речі (§2) він дає такі, яких markdown не
дає в принципі, і кожна окупається не тут:

- **Порядок артефактів, який не обійти** — у команді, де спокуса почати з коду
  висока.
- **Exit-код для CI** — коли специфікацію перевіряють автоматично, а не очима.
- **Специфікація як дані** — на дистанції в десятки специфікацій.

**Найкорисніше:** не артефакти, а зауваження до моєї ж специфікації — §3.1
Task A за критерієм OpenSpec є design'ом, а не spec'ом (§2).

**Ціна:** 2 хв налаштування + 40 хв на артефакти, з яких ~35 хв — рішення, які
я приймала б і без інструмента. Чистий overhead ≈ 7 хвилин.
